# Этап 1: пауза на выборе схемы доступа с iPhone

Дата фиксации: 2026-08-09.

Статус: работа приостановлена по просьбе пользователя. Инфраструктура WebRTC
работает, но физический iPhone пока не смог открыть тестовую PWA. До выбора
новой DNS/hostname-схемы дальнейшие изменения не выполнять.

## Что уже доказано

Сама инфраструктура этапа 1 исправна:

- Apache на `192.168.50.10` отдает тестовую PWA;
- WSS proxy соединяет браузер с локальным WebSocket Asterisk;
- отдельный PJSIP endpoint `1099` регистрируется;
- Echo `600` установил WebRTC-сессию;
- ICE дошел до `connected`;
- автоматический LAN-тест подтвердил двусторонний RTP без потерь;
- рабочий Linphone/HFP/cellular маршрут не заменялся.

Автоматический тест использовал принудительное соответствие
`home.example.net -> 192.168.50.10`. Поэтому он не проверял реальное
разрешение имени и поведение iCloud Private Relay на iPhone.

Физическая матрица foreground/background/lock screen еще не начиналась. Это
не `NO-GO` по WebRTC: тест заблокирован раньше, на доступе к HTTPS origin.

## Фактическая сетевая картина

### Публичные записи и HTTPS

- `home.example.net` имеет A `192.0.2.5`.
- `192.0.2.5` совпадает с реальным домашним публичным IPv4, поэтому исходная
  трактовка этого адреса как чужого/устаревшего была неверной.
- HTTPS на публичном `192.0.2.5:443` возвращал сертификат Microsoft и затем
  `400 Invalid URL`, а не домашний Apache virtual host.
- Это означает, что публичный TCP/443 обслуживает другой endpoint/decoy.
  Поведение согласуется с имеющимся дома Xray/camouflage, но его конфигурация
  в рамках этой диагностики не менялась.
- При прямом направлении имени на `192.168.50.10:443` сертификат и PWA
  работают корректно.

### Устаревшая AAAA

DuckDNS дополнительно возвращал:

```text
2001:db8:1::10
```

Ни `192.168.50.20`, ни `192.168.50.10` не имеют этого адреса или глобального
IPv6 default route. Перехват показал повторные SYN от
`fd00:50::4` к этому адресу на `8443` без ответа.

AAAA очищена через штатный DuckDNS API. A `192.0.2.5` сохранена. После
изменения Cloudflare `192.0.2.6` и Google `192.0.2.7` возвращали A и no-data для
AAAA.

Резервная фиксация прежних записей:

```text
/var/backups/asterisk-pwa-duckdns/20260809-215928
```

### VPN и iPhone

- iPhone peer: `10.77.77.4`, IPv6 peer: `fd00:50::4`.
- Handshake оставался свежим во всех проверках.
- Split-tunnel профиль успешно подключался, но Safari-трафик к публичному
  origin обходил маршруты приватной LAN.
- Full-tunnel профиль также успешно подключился; счетчики peer существенно
  росли, то есть `0.0.0.0/0, ::/0` реально применялись.
- VPN-to-LAN трафик на `.152` маскируется в `192.168.50.20`; существующий ACL
  Apache разрешает этот источник.

## Почему обычный split DNS не решил проблему

На `192.168.50.20` развернут `dnsmasq`:

- слушает только `10.77.77.1:53` на `awg0`;
- возвращает `home.example.net -> 192.168.50.10`;
- не возвращает AAAA для этого имени;
- пересылает остальные запросы на `192.168.50.1`.

Сервис и ответы проверены локально. Однако два синхронных перехвата показали:

- Safari не отправлял запросы на `10.77.77.1:53` даже для нового случайного
  имени `.invalid`;
- при full tunnel iPhone многократно передавал зашифрованный трафик к
  `192.0.2.6:443/UDP`;
- также наблюдались соединения к Apple relay на UDP/443;
- следовательно, строка `DNS = 10.77.77.1` в AmneziaWG не может подменить
  DNS внутри Private Relay/защищенного resolver path.

Требование отключить Private Relay, Cloudflare encrypted DNS или общую защиту
телефона признано неприемлемым. Это не должно быть эксплуатационным условием
телефона.

## Проверенный, но не сработавший hairpin

На `.152` установлен узкий динамический nftables hairpin:

```text
iif awg0
source 10.77.77.4
destination <текущий A home.example.net>
TCP ports 443 or 8443
DNAT -> 192.168.50.10:443
```

Идея: сохранить внешний DNS и сертификат, но перехватить соединение к
домашнему WAN внутри full-tunnel VPN.

Результат:

- для обычного URL на 443 счетчик DNAT остался нулевым;
- для URL с `:8443` сначала использовалась устаревшая AAAA;
- после удаления AAAA повторный запрос на `8443` не появился на `awg0` и
  счетчик DNAT остался нулевым;
- домашний Apache не получил ни одного запроса iPhone.

Вывод: Safari/Private Relay выполняет origin-соединение через внешний relay,
поэтому VPN-шлюз видит туннель к relay, но не видит TCP-соединение к домашнему
WAN, которое можно было бы DNAT-ить.

Hairpin сейчас остается установленным, но фактически не используется:

```text
/usr/local/sbin/asterisk-pwa-hairpin
/etc/cron.d/asterisk-pwa-hairpin
nft table ip asterisk_pwa_hairpin
```

Резервные копии:

```text
/var/backups/asterisk-pwa-vpn-hairpin/20260809-214602
/var/backups/asterisk-pwa-vpn-hairpin/20260809-214854
```

После выбора окончательной схемы hairpin следует либо удалить, либо явно
включить в принятую архитектуру. Сейчас полагаться на него нельзя.

## Разумные варианты продолжения

### Вариант A: private A для существующего имени

Публичный resolver возвращает:

```text
home.example.net -> 192.168.50.10
```

Плюсы:

- encrypted DNS и Private Relay не требуется отключать;
- локальное назначение должно идти напрямую через VPN;
- существующий сертификат остается действительным;
- можно вернуться к split-tunnel профилю.

Риск: если `home.example.net` используется вне VPN, такой переход
сломает внешний доступ. Перед изменением нужен ответ пользователя, используется
ли это имя где-либо еще.

### Вариант B: отдельное имя только для PWA

Создать отдельный hostname, например отдельный DuckDNS domain, с public A,
указывающей на `192.168.50.10`, и получить отдельный сертификат через DNS-01.

Плюсы:

- не затрагивает существующий `home-example`;
- сохраняет защиту iPhone;
- чисто отделяет VPN-only PWA от публичного Xray/HTTPS origin;
- лучше соответствует финальной архитектуре.

Минус: нужно зарегистрировать новое DNS-имя и настроить выпуск/renewal
сертификата. Это наиболее безопасный рекомендуемый вариант, если существующее
имя имеет другие потребители.

### Вариант C: публичный origin, совместимый с Private Relay

Опубликовать отдельный HTTPS origin/порт наружу и добавить сильную
аутентификацию, например mTLS. Это сложнее, увеличивает внешнюю поверхность и
не соответствует первоначальной идее VPN-only доступа. Для этапа 1 не
рекомендуется без отдельного решения.

## Точка возобновления

Первый вопрос после паузы:

> Используется ли `home.example.net` для чего-либо вне VPN?

Далее:

1. Если нет — временно перевести его A на `192.168.50.10`, проверить ответ
   через Cloudflare и повторить Safari/PWA test.
2. Если да — зарегистрировать отдельное имя, настроить private A и DNS-01
   certificate.
3. После успешного открытия PWA вернуть split-tunnel профиль, если full tunnel
   не нужен.
4. Удалить ненужный hairpin и, если private public-DNS answer полностью решает
   доступ, решить, оставлять ли `dnsmasq`.
5. Только затем начинать foreground Echo `600` и исходную iOS background
   matrix из `STAGE1_WEBRTC_PWA_RESULTS.md`.

До ответа пользователя DNS A существующего имени не менять и новый hostname
не создавать.
