с private A и DNS-01 сертификатом.

## Цель

Сделать минимальный телефон для удаленного iPhone, работающий с домашней израильской SIM через существующую цепочку:

```text
cellular <-> домашний iPhone <-> Bluetooth HFP <-> chan_mobile/Asterisk
                                                    <-> WebRTC/PWA на удаленном iPhone
```

Клиент должен быть self-hosted и доступен через существующую VPN. Желательно отказаться от push-инфраструктуры Linphone и других внешних VoIP-сервисов.

Нужные функции клиента:

- набор номера, Call;
- Answer, Reject, Hangup;
- DTMF и Mute;
- вставка номера через Paste;
- список последних набранных номеров;
- Caller ID и состояние вызова.

Не нужны видео, чат, presence, конференции, несколько SIP-аккаунтов и сложная телефонная книга.

## Подтвержденное текущее состояние

- Asterisk 20.6.0 работает на `192.168.50.10`.
- Домашний iPhone подключен через Bluetooth HFP/MAP и `chan_mobile`.
- Исходящий звонок через Linphone -> Asterisk -> HFP -> cellular проверен ранее.
- Пользователь 2026-08-09 дополнительно подтвердил, что входящий звонок до Linphone работает как задумано и Caller ID отображается.
- Следовательно, cellular/HFP/Asterisk/SIP-маршрут и Caller ID не являются текущим блокером.
- Проблема Linphone: после сворачивания на iOS приложение теряет регистрацию; push Linphone решает это через внешнюю инфраструктуру.
- VPN-шлюз находится на `192.168.50.20`; телефон и домашняя инфраструктура доступны друг другу как узлы виртуальной локальной сети.
- На `.128` уже работает Apache на 443 с действующим Let's Encrypt сертификатом и модулями reverse proxy/WebSocket.
- В установленном пакете Asterisk имеются необходимые модули WebRTC/WSS, включая `res_http_websocket`, `res_pjsip_transport_websocket`, crypto/DTLS и Opus.
- Сейчас Asterisk слушает обычный SIP/UDP на `192.168.50.10:5060`; WebSocket-транспорт еще не настроен.

Общий контекст существующей Asterisk/HFP-системы находится в `CONTEXT.md`.

## Главный результат исследования

PWA-подход технически разумен как небольшой proof of concept и потенциально как телефон, который пользователь держит открытым во время разговора.

Его нельзя заранее считать полноценной заменой native softphone:

- у PWA нет CallKit и PushKit;
- нет системного экрана входящего звонка и ответа с lock screen;
- iOS не гарантирует продолжение произвольной сетевой работы, WebRTC uplink и микрофона после сворачивания или блокировки;
- переключение приложений, блокировка, Siri и обычный cellular-вызов могут прервать разговор;
- надежность активного разговора в фоне необходимо проверить на конкретном актуальном iPhone/iOS.

Web Push поддерживается установленными на Home Screen web-приложениями с iOS/iPadOS 16.4. Разрешение должно запрашиваться после явного действия пользователя. Silent push запрещен: каждый push должен сразу показывать уведомление.

Backend, SIP и WebRTC можно разместить полностью дома, но доставка Web Push на iPhone все равно использует Apple Push Notification Service. Таким образом, зависимость от Linphone/Twilio/Flexisip устраняется, но зависимость от инфраструктуры Apple остается. Домашнему серверу нужен исходящий HTTPS-доступ к Apple; публичный входящий endpoint для push не требуется.

## Рекомендуемая архитектура

### Web и signaling

- Использовать существующий Apache и сертификат на `.128`.
- Отдавать минимальную PWA, например, в `/phone/`.
- Проксировать `/asterisk-ws` по WSS к локальному HTTP WebSocket Asterisk.
- Проксировать `/phone/api` к небольшому backend.
- Ограничить PWA, API и WSS адресами VPN на Apache и firewall.
- Не публиковать обычные SIP-порты наружу.

При reverse proxy Asterisk видит адрес proxy, а не исходный IP браузера. Поэтому контроль VPN-источника нужно выполнять на Apache/VPN firewall, а не полагаться только на PJSIP ACL.

### PJSIP/WebRTC endpoint

Создать отдельный endpoint только для PWA:

- WSS;
- DTLS-SRTP;
- ICE, AVPF и `rtcp_mux`;
- `direct_media=no`;
- один контакт/один аккаунт;
- отдельные credentials;
- строгий исходящий dialplan с разрешенными направлениями.

TURN сначала не ставить. При VPN браузер должен иметь возможность передавать ICE/RTP непосредственно Asterisk. TURN внутри VPN добавлять только при доказанной проблеме с ICE или сменой сетей.

### Клиент

Первый кандидат — SIP.js `SimpleUser`:

- API соответствует одному аккаунту и одному одновременному звонку;
- уже есть connect/register/call/answer/decline/hangup/mute/DTMF;
- SIP.js широко использовался с Asterisk, в том числе Browser-Phone;
- требуется зафиксировать конкретную версию и выполнить Safari/iOS regression tests;
- DTMF настроить как RTP/RFC4733, не полагаться на SIP INFO.

JsSIP остается запасным вариантом, если SIP.js покажет конкретную проблему с Safari, Asterisk или необходимыми состояниями. Клиент следует строить через небольшой внутренний SIP-адаптер, чтобы библиотеку можно было заменить без переписывания UI.

Предпочтительный frontend — простой TypeScript без тяжелого framework. Service worker выполняет только Push/Notification и не пытается держать SIP-регистрацию или звонок.

Caller ID и активное состояние можно получать из `/phone/api/active-call`; это также позволяет не зависеть от ограниченного delegate API `SimpleUser`.

### Backend

Небольшой локальный сервис, например Node.js:

- библиотека `web-push` и собственные VAPID keys;
- хранение одной или нескольких PushSubscription в SQLite;
- авторизация PWA/API;
- соединение с Asterisk AMI;
- таблица активного вызова: call ID, Asterisk `UNIQUEID`, channel, Caller ID, состояние и время;
- endpoints для active-call, reject, subscription и health;
- короткий журнал временных меток для PoC.

Push может содержать общий текст `Входящий звонок`, а Caller ID загружаться после открытия через VPN. Это уменьшает объем персональных данных в уведомлении. Если Caller ID нужен прямо на lock screen, его можно включить в зашифрованный Web Push payload после отдельного решения пользователя.

### Входящий вызов и late attach

Предпочтительный первый вариант — стандартная очередь Asterisk:

```text
chan_mobile inbound
    -> Ringing(), но не Answer()
    -> UserEvent/AMI с UNIQUEID, channel и Caller ID
    -> Queue(pwa-inbound)

backend
    -> Web Push

notification tap
    -> PWA открывается
    -> проверяет /active-call
    -> подключает WSS и регистрирует PJSIP endpoint
    -> Queue видит доступного member и отправляет SIP INVITE
    -> пользователь нажимает Answer
    -> Asterisk соединяет WebRTC и HFP
```

Предполагаемые параметры Queue:

- статический member `PJSIP/pwa-phone`;
- `joinempty=yes`;
- `leavewhenempty=no`;
- небольшой `retry`;
- `ringinuse=no`;
- ringback вместо music on hold.

Ключевая непроверенная гипотеза: Queue должна продолжать держать вызывающего и позвонить endpoint после его поздней регистрации. Это необходимо доказать в PoC. Также нужно проверить, что до Answer на PWA cellular-канал действительно остается неотвеченным и вызывающий слышит нормальный ringback.

Reject выполняется идемпотентным запросом к backend. Backend завершает только канал, точно сопоставленный с call ID/`UNIQUEID`, через AMI `QueueWithdrawCaller` или `Hangup`. Если вызывающий уже отключился, PWA показывает, что звонок завершен, и не пытается отвечать на устаревший push.

Если Queue плохо работает с поздней регистрацией или возникают гонки, запасной вариант — ARI holding bridge:

1. входящий канал передается в Stasis/holding bridge;
2. backend отправляет push;
3. после регистрации PWA backend originate-ит WebRTC endpoint;
4. после Answer оба канала соединяются в mixing bridge.

ARI дает более точный контроль, но добавляет собственную логику состояний, поэтому не является первым выбором.

### Исходящий вызов

```text
PWA -> SIP/WSS -> отдельный PJSIP context
    -> нормализация и проверка номера
    -> Mobile/<домашний-iPhone>/<номер>
    -> cellular
```

Существующий рабочий маршрут Linphone на этапе PoC сохраняется как контрольный и аварийный путь.

## Оценка найденных проектов

### InnovateAsterisk/Browser-Phone

Полезен как эталон рабочей интеграции SIP.js/Asterisk, обработки медиапотоков, состояний вызова, DTMF и reconnect. Не рекомендуется как основа проекта: большой монолитный `phone.js`, много ненужных функций, старые web-зависимости и отсутствие Web Push.

### SIP.js

Лучший первый кандидат благодаря `SimpleUser` и минимальному API. Его published release не новый, поэтому нужна фиксация версии и реальные iOS-тесты.

### JsSIP

Зрелая и более активно обновляемая альтернатива. Потребует больше собственного кода для session/media state. Использовать при конкретной проблеме SIP.js, а не реализовывать сразу два клиента.

### AgentoxAI Titan Dialer

Не решает целевой сценарий. В найденной реализации push отправляется как уведомление о пропущенном вызове после завершения попытки Twilio, а не будит PWA для подключения к еще ожидающему вызову. Проект имеет мало истории и не должен быть донором серверной архитектуры. Допустимо посмотреть только небольшие UI/PWA-фрагменты.

### Flexisip/OpenSIPS и полноценные softphone-платформы

Избыточны для одного домашнего endpoint и существующего Asterisk. Flexisip может self-host push proxy, но приносит полноценную дополнительную SIP-инфраструктуру и не устраняет фундаментальные ограничения iOS PWA.

### Native fallback

Если PWA не выдержит тест блокировки/фона, надежный путь — минимальное native iOS-приложение на Linphone SDK с собственным APNs/VoIP Push backend и CallKit. Серверный backend, Asterisk-маршрутизация и Queue/ARI могут остаться теми же. Цена этого варианта — Apple Developer signing, APNs credentials и сопровождение native-приложения.

## План реализации proof of concept

PoC делится на три последовательных этапа с возможностью остановить проект после каждого из них. Полный интерфейс телефона разрабатывается только после успешного прохождения всех трех этапов.

### Этап 1. WebRTC в установленной PWA и поведение iOS в фоне

Цель этапа — с минимальным количеством собственного кода проверить наиболее опасный риск: остается ли практически работоспособным WebRTC-аудиозвонок после переключения приложения, блокировки экрана и сетевых изменений. Web Push, Queue и late attach на этом этапе не разрабатываются.

#### Изолированный WebRTC endpoint Asterisk

Добавляется отдельный тестовый endpoint, например `pwa-probe`:

- SIP signaling только через WSS;
- DTLS-SRTP, ICE, AVPF и `rtcp_mux`;
- `direct_media=no`;
- отдельные credentials;
- один контакт и один одновременный вызов;
- отдельный ограниченный dialplan context;
- сначала только необходимые аудиокодеки.

Существующий Linphone endpoint и его рабочие маршруты не заменяются.

#### Локальный WebSocket Asterisk

- Включается HTTP/WebSocket-интерфейс Asterisk.
- Встроенный HTTP-сервер привязывается к localhost или другому минимально необходимому адресу.
- Наружу порт встроенного HTTP-сервера Asterisk не публикуется.
- Перед изменениями сохраняются резервные копии затрагиваемых конфигурационных файлов.

#### HTTPS/WSS через существующий Apache

На существующем HTTPS virtual host создаются отдельные пути:

```text
/phone-probe/    тестовая установленная PWA
/asterisk-ws     WebSocket reverse proxy к Asterisk
```

Используется существующий доверенный TLS-сертификат. Доступ ограничивается VPN-сетью на Apache/firewall. Новый web-сервер и новый публичный SIP-порт не создаются.

#### Browser-Phone как одноразовый измерительный клиент

- Разворачивается зафиксированная версия Browser-Phone.
- Все требуемые runtime-файлы размещаются локально, без зависимости от внешних CDN.
- Используется только один тестовый SIP-аккаунт.
- Проверяются manifest, service worker, `display: standalone` и установка на Home Screen.
- Browser-Phone не считается основой будущего UI и не подвергается большому рефакторингу.
- Credentials не записываются в Git или документацию.

Browser-Phone выбран для этапа 1 как готовый проверенный SIP.js/Asterisk-клиент. Это позволяет исследовать ограничения iOS, не смешивая их с ошибками нового собственного softphone.

#### Тестовый dialplan

Добавляются только контролируемые тестовые направления:

- `600` — Echo для проверки микрофона и обратного звука;
- отдельный тестовый исходящий маршрут через `chan_mobile`;
- при необходимости входящий вызов на WebRTC endpoint, только когда PWA уже открыта и зарегистрирована.

Рабочий входящий маршрут Linphone не переключается. Тестовый маршрут не должен пересекаться с обычной эксплуатацией.

#### Минимальная диагностика

Необходим небольшой диагностический слой, фиксирующий:

- начало и завершение звонка;
- `visibilitychange`, `pagehide`, `pageshow`, `online` и `offline`;
- состояние SIP-регистрации после возврата;
- разрыв и восстановление WebSocket;
- наличие RTP и звука в каждом направлении;
- возможность Mute и Hangup после возврата.

Диагностические записи должны сохраняться до возврата в PWA и позволять сопоставить клиентские события с журналом Asterisk. Полноценный backend и база данных для этого не нужны.

#### Матрица испытаний на реальном iPhone

После добавления PWA на Home Screen выполняются:

1. Echo и разговор в foreground не менее 10 минут.
2. Переключение в другое приложение на 5, 30 и 120 секунд.
3. Блокировка экрана на 5, 30 и 120 секунд.
4. Несколько циклов background/foreground в одном звонке.
5. Разговор через реальный маршрут `chan_mobile`/HFP/cellular.
6. Wi-Fi -> cellular и обратно при активной VPN.
7. Краткая потеря VPN на 5 и 30 секунд.
8. Открытие Control Center и вызов Siri.
9. Обычный входящий cellular-вызов на удаленном iPhone.
10. Новый звонок после поврежденной или неожиданно завершенной сессии.

Для каждого сценария отдельно отмечается:

- слышит ли удаленная сторона микрофон PWA;
- продолжает ли PWA воспроизводить удаленный звук;
- жив ли SIP dialog;
- продолжает ли идти RTP;
- восстановились ли управление, Mute и Hangup;
- возможен ли следующий звонок без перезагрузки PWA.

После потери VPN не требуется доказывать бесшовное восстановление текущего звонка. Минимально приемлемое поведение — корректно обнаружить потерю вызова, восстановить WSS/регистрацию после возврата сети и быть готовым к следующему звонку.

#### Результат этапа 1

Должны быть получены:

- работающий URL тестовой PWA;
- отдельный WebRTC endpoint;
- WSS через Apache;
- изолированный тестовый dialplan;
- таблица фактического поведения iPhone;
- файл `STAGE1_WEBRTC_PWA_RESULTS.md` с условиями и результатами;
- решение `GO`, `GO с ограничением foreground` или `NO-GO`.

Ожидаемый объем: примерно половина или один рабочий день на развертывание и первичную проверку плюс время на повторяемые испытания.

#### Что не меняется на этапе 1

- Linphone и его endpoint;
- подтвержденный входящий маршрут и Caller ID;
- `chan_mobile`, Bluetooth/HFP и MAP/SMS;
- версия Asterisk;
- VPN-шлюз и топология VPN, если не обнаружена конкретная проблема маршрутизации;
- production dialplan и обычный SIP-клиент как fallback.

### Этап 2. Web Push, холодный запуск и доступ к микрофону

Выполняется только после приемлемого результата этапа 1:

- минимальная собственная PWA без SIP-телефонии;
- notification permission и push subscription по явной кнопке;
- предварительное получение microphone permission;
- небольшой backend на `web-push` с собственными VAPID keys;
- обычный и declarative Web Push;
- измерение push -> notification -> tap -> видимая PWA;
- закрытая/выгруженная PWA, lock screen, Wi-Fi/cellular, VPN on/off и Focus modes;
- проверка, доступна ли домашняя инфраструктура после tap и поднимается ли VPN on demand.

Этап должен ответить, достаточно ли быстро и надежно push открывает приложение и можно ли после явного нажатия Answer получить микрофон. Ожидаемый собственный код: примерно 150-250 строк, срок — около половины или одного рабочего дня плюс серия повторов.

### Этап 3. Late attach к ожидающему входящему вызову

Выполняется только после успешных этапов 1 и 2:

- AMI backend и состояние одного активного звонка;
- Asterisk Queue с поздно появляющимся WebRTC member;
- `UserEvent` с `UNIQUEID`, channel и Caller ID;
- push, tap, `/active-call`, WSS, REGISTER, INVITE, Answer и bridge;
- Reject до и после INVITE;
- вызывающий отключается до открытия PWA;
- устаревший/повторный push;
- явно заданное поведение для второго параллельного звонка.

Записываются временные точки:

```text
t0 Asterisk увидел входящий вызов
t1 push request принят push service
t2 notification tap / PWA стала видимой
t3 WSS connected
t4 SIP registered
t5 INVITE получен
t6 пользователь нажал Answer
t7 медиамост создан, RTP идет в обе стороны
```

Ожидаемый собственный код этапа: примерно 200-400 строк, срок — 1-2 рабочих дня. Если Queue не работает надежно с поздней регистрацией, отдельно принимается решение об ARI holding bridge; это не входит в исходный объем трех этапов.

После прохождения всех трех этапов можно проектировать окончательный минимальный UI: keypad, Paste, recents, Call/Answer/Reject/Hangup, DTMF, Mute, Caller ID и индикаторы состояния.

## Критерии Go/No-Go

Предлагаемый минимум перед развитием интерфейса:

- не менее 19 успешных cold incoming попыток из 20 в каждом основном сетевом режиме;
- приемлемый p95 от tap до готовности Answer;
- отсутствие одностороннего аудио;
- отсутствие преждевременного Answer на cellular/HFP leg;
- корректный отбой при раннем завершении звонка;
- понятное и приемлемое для пользователя поведение при блокировке и сворачивании.

Если разговор требует постоянно открытой PWA и это приемлемо, проект можно продолжать как простой self-hosted foreground-телефон.

Если обязательны lock-screen, надежная многозадачность и системное поведение обычного телефона, PWA следует отклонить как основной клиент и перейти к native CallKit-варианту. Смена SIP.js на JsSIP не исправит отсутствие системных iOS capabilities.

## Что не менять до результатов PoC

- рабочий Linphone endpoint и проверенный входящий маршрут;
- `chan_mobile`, Bluetooth/HFP и MAP/SMS-настройки;
- существующий обычный SIP-клиент как fallback;
- версию Asterisk во время первичного эксперимента;
- VPN-топологию, если тест не докажет конкретную проблему маршрутизации.
