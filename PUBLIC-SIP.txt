Входящий SIP из интернета — рабочая конфигурация 14 ноября 2026

Результат
Пользователь подтвердил звонки из Linphone на стационарный T780P из домашней
Wi-Fi-сети и извне: речь в обе стороны, отбой со стационарного завершает
вызов в Linphone. Разговоры короткие; длительная стабильность не измерена.
Действующий внешний путь использует IPv4.

Что вводить в Linphone 6.2.2 на iPhone
  1002@home.example.net:5061;transport=tls
Полный SIP URI для других интерфейсов:
  sip:1002@home.example.net:5061;transport=tls

«Звонки» -> трубка со знаком + -> строка поиска с лупой. Крестиком полностью
очистить строку, вставить первый вариант без sip: и без начального двоеточия,
нажать появившийся адрес. Выбран аккаунт traveler-example@sip.linphone.org.
SIM-карта не нужна. Стационарный вызывает личный Linphone номером 612:
подробности в LINPHONE-CALLS.txt.

Отдельный аккаунт Asterisk у Linphone не создавался и не регистрировался.
В проверенном клиентском маршруте Linphone обращается непосредственно
к публичному Asterisk по TLS. Отдельно подтверждена серверная маршрутизация
через sip.linphone.org служебными запросами; это другая проверка.

Топология и ограничения
  Интернет TCP 5061 -> роутер -> 192.168.50.10 TCP 5062 (TLS).
  Интернет UDP 10000–10015 -> .128, каждый порт в тот же внутренний порт.
  Asterisk -> enp3s0 10.77.0.1/30 -> T780P 10.77.0.2, endpoint 1002.
  enp4s0 192.168.50.10/24 соединяет сервер с домашним роутером.

Публичный endpoint требует SRTP/SDES, use_avpf=yes, кодеки alaw/ulaw.
Он принимает использованный Linphone профиль RTP/SAVPF; другие профили
отдельно не проверялись. direct_media=no оставляет оба плеча через Asterisk.
На выделенном кабеле T780P остаётся обычный RTP: интернет-шифрование
не является сквозным до стационарного.

Публичный контекст from-public-sip содержит только 1002, без выхода к 612
или сотовым маршрутам. REFER и SUBSCRIBE запрещены. Перед Dial проверяются
защищённый SIP-канал и адрес приёма 192.168.50.10:5062. Номер доступен извне
без регистрации; заголовок To выбирает назначение, но не удостоверяет
личность вызывающего. Логин и пароль телефона не менялись. Мобильные
маршруты и 612 сохранены; сотовый разговор после этих настроек не повторялся.

На .128 в момент настройки не было глобального IPv6. Публичный IPv6-вход
SIP и проход через IPv6-фильтр роутера этим этапом не настроены/не проверены.
При возвращении AAAA отдельно проверить и настроить SIP/RTP по IPv6
и переход клиента на IPv4 при недоступном IPv6. Проверка IPv4 этого не доказывает.
Обновление A/AAAA и удаление устаревшей AAAA исправлены независимо:
network/duckdns/README.txt. На момент проверки A=192.0.2.2, AAAA отсутствовала.
Адрес динамический, для набора использовать DNS-имя.

Установленные настройки
  /etc/asterisk/pjsip_public.conf
  /etc/asterisk/extensions_public.conf
  В pjsip.conf и extensions.conf добавлены include этих файлов.
  /etc/asterisk/rtp.conf: rtpstart=10000, rtpend=10015.
  /etc/asterisk/dnsmgr.conf: enable=yes, refreshinterval=300.

Диапазон RTP общий: 16 UDP-портов, 8 пар RTP/RTCP, обычно до четырёх
одновременных SIP-разговоров с двумя звуковыми плечами каждый. Для расширения
увеличивать его согласованно с роутером/UFW. Сужение диапазона ограничивает
ёмкость; это не оптимизация качества звука.

Global endpoint_identifier_order: ip,header,username,anonymous.
Identify сопоставляет To с SIP/SIPS-адресом 1002@home.example.net.
У transport-tls-public:
  bind=192.168.50.10:5062, protocol=tls, method=tlsv1_2;
  local_net=192.168.50.10/32 и local_net=10.77.0.0/30;
  external_signaling_address=home.example.net;
  external_signaling_port=5061;
  external_media_address=home.example.net.
Не заменять /32 на домашнюю /24: hairpin-вызов приходит от роутера,
но должен получать публичные Contact/SDP. С /24 Asterisk возвращал
внутренний Contact, клиент не присылал ACK, завершение вызова зависало.
После исправления проверены ACK и BYE/200 OK.
На обоих плечах используется прежний RtpSourceReset — обход дефекта
дистрибутивного RTP-патча; исходники и сборка в recovery/2026-11-14/.

Роутер Sagemcom 192.168.50.1: 17 отдельных правил
  uid=9, Alias=PORTFW_RULE_6: TCP 5061 -> .128:5062, Asterisk SIP TLS.
  uid=10..25, Alias=PORTFW_RULE_7..22: UDP 10000..10015 -> тот же порт .128.
  Для каждого UDP-правила ExternalPortEndRange=0 (один порт).
Все 17 правил Enable=true, Status=ENABLED. Пять прежних пользовательских
правил и скрытая запись DMZ не изменены.

Особенность проверенного API: одна запись диапазона 10000–10199
с InternalPort=10000 направляла все пакеты на внутренний 10000.
Проверено для внешних 10000, 10002 и 10198. Это была неверная первоначальная
настройка агента. InternalPort=0 также не решил проблему. Итоговое решение —
16 отдельных правил; все 16 назначений проверены доставкой пакетов.

В UFW .128 добавлены два разрешения на enp4s0 к 192.168.50.10:
  TCP 5062, комментарий Public Asterisk TLS;
  UDP 10000:10015, комментарий Public Asterisk SRTP.
Прежние правила сохранены, промежуточное 10000:10199 удалено.
UDP 5060 в интернет не открывался.

Сертификат и продление
Использован существующий Let's Encrypt для home.example.net,
действовавший с 15 октября 2026 до 13 января 2027.
  Источник: /etc/letsencrypt/live/home.example.net/
  Копии: /etc/asterisk/keys/public-sip/{fullchain.pem,privkey.pem}
  Каталог root:asterisk 0750, файлы root:asterisk 0640.
  Hook: /etc/letsencrypt/renewal-hooks/deploy/asterisk-public-cert.sh
Hook проверяет имя, срок и соответствие ключа сертификату, обновляет копии
через временные файлы, выполняет reload res_pjsip. Другие сертификаты
и прежние Apache hooks не меняет; одинаковые файлы повторно не обновляет.
Asterisk 20.6 поддерживает обновление сертификата при неизменных путях
без allow_reload=yes. Проверка имени/цепочки TLS прошла; реальное продление
новым сертификатом пока не происходило. Приватный ключ в исходники не включён.

Причины первоначальных отказов приложения
Журнал Linphone показал попытку UDP 5060 при вводе sips:-адреса.
При редактировании получился адрес с лишним начальным двоеточием;
клиент преобразовал его в некорректное имя у sip.linphone.org и получил
400 Bad To Header. Происхождение лишнего двоеточия точно не установлено.
Очистка поля и рабочий адрес с явным transport=tls устранили этот отказ.
После доставки INVITE потребовался use_avpf=yes для предложенного RTP/SAVPF.
Затем исправлены Contact при hairpin и проброс UDP, описанные выше.
Это отдельные причины от двух ранее доказанных ошибок chan_mobile/translate.c.

Восстановление
Из локального корня /home/gateway/asterisk:
  sha256sum -c network/SHA256SUMS
Сначала сохранить нынешние файлы/правила. Архив распаковать отдельно,
сравнить и перенести только нужные настройки, сохраняя новые изменения,
учётные данные и права. Не распаковывать прямо поверх корня сервера.
Старые .so нельзя ставить на новый ABI без пересборки:
порядок в recovery/2026-11-14/RESTORE.txt.

На существующей установке восстановить public-конфиги, include, rtp.conf
и dnsmgr.conf выборочно; копии сертификата получить hook из текущего
Certbot lineage. Сверить роутер/UFW. При 0 звонков:
  asterisk -rx 'dnsmgr reload'
  asterisk -rx 'module reload res_rtp_asterisk.so'
  asterisk -rx 'module reload res_pjsip.so'
  asterisk -rx 'dialplan reload'
Не все параметры транспорта меняются reload: сверять pjsip show transport.
При необходимости штатный restart Asterisk выполнять в согласованный
перерыв без активных звонков. Перезагрузка всего сервера не нужна.

deploy-server.py рассчитан на первоначальную установку на .128 от root.
Повтор поверх существующего pjsip_public.conf намеренно прекращает.
Он не настраивает роутер и UFW. Для первоначальной установки отдельно:
  Локально, с действующим доступом из /home/gateway/Router:
    python3 /home/gateway/asterisk/network/public-sip/router-forwarding.py --apply
  От root на .128, после сверки существующих UFW-правил:
    ufw allow in on enp4s0 proto tcp from any to 192.168.50.10 port 5062 comment 'Public Asterisk TLS'
    ufw allow in on enp4s0 proto udp from any to 192.168.50.10 port 10000:10015 comment 'Public Asterisk SRTP'
Скрипт роутера без флага только читает. При конфликтах останавливается,
не перезаписывая чужие правила; секреты получает из существующего keyring.

Проверки без вызова стационарного, из локального корня проекта:
  python3 network/public-sip/probe.py
  python3 network/public-sip/probe.py --host home.example.net --port 5061
Это OPTIONS 1002 и отклоняемый INVITE 612. Затем регистрация 1002,
Bluetooth, маршруты и согласованные реальные разговоры: входящий снаружи,
612, сотовые в обоих направлениях, речь и отбой с обеих сторон.

Откат публичного SIP
Исходная резервная папка на .128:
  /var/backups/asterisk-public-sip/20261114-181138/
Manifest содержит исходные права/владельцев/хеши. Файлы под etc/ относятся
к началу настройки; поздние *before-avpf*, *before-hairpin* и
rtp-before-single-port-rules.conf — промежуточные состояния, не полный откат.
Закрыть только новые правила роутера:
  python3 /home/gateway/asterisk/network/public-sip/router-forwarding.py --rollback
Скрипт удаляет только 17 точно совпадающих управляемых правил.
На .128 удалить два добавленных UFW-разрешения:
  ufw delete allow in on enp4s0 proto tcp from any to 192.168.50.10 port 5062
  ufw delete allow in on enp4s0 proto udp from any to 192.168.50.10 port 10000:10015
При отсутствии разговоров убрать public-конфиги и их include; вернуть
прежний RTP 10000–20000 и dnsmgr с учётом последующих правок.
Удалить только новый Certbot hook; Let's Encrypt и Apache не трогать.
Выполнить reload, перечисленные выше. Для удаления listener из памяти
может понадобиться штатный restart Asterisk в согласованный перерыв:
роутер/UFW уже закрывают внешний доступ. Проверить 1002, Bluetooth и 612.
Исправление DuckDNS сохраняется независимо от отката SIP; его отдельный
откат описан в network/duckdns/README.txt.
