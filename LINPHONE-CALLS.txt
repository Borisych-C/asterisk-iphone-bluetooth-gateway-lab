Исправление отказа до ответа — 14 ноября 2026

Исходный вызов длился 6 секунд, без ответа. Повторная SIP-трассировка показала:
Linphone server: 407 (обычная авторизация), 100, 110 Push sent;
через примерно 5 секунд приложение LinphoneiOS/6.2.2 (SDK 5.5.0) вернуло
488 Not acceptable here. Asterisk передал отказ стационарному, Q.850 cause=58.
Ответа 180 Ringing не было, поэтому стационарный не включал гудки ожидания.
Рингтон iPhone был вызван push-уведомлением до приёма SIP INVITE приложением.

Пользователь подтвердил в Linphone: SRTP, шифрование обязательно.
В исходном предложении Asterisk был RTP/AVP без шифрования.
В /etc/asterisk/pjsip_linphone_push.conf включены:
  media_encryption=sdes
  media_encryption_optimistic=no
  transport=transport-tls-linphone
  outbound_proxy=sip:sip.linphone.org:5061\;transport=tls\;lr
Новый transport-tls-linphone: TLS 1.2, bind 192.168.50.10:5061,
ca_list_file=/etc/ssl/certs/ca-certificates.crt, verify_server=yes.
Настройки паролей и аутентификации не изменены. Ключи SRTP передаются внутри TLS.
Это шифрование участка Asterisk—Linphone, не сквозное шифрование до T780P:
стационарный продолжает использовать RTP на выделенном кабеле.

При первом добавлении TLS простого module reload res_pjsip.so недостаточно:
transport уже виден в CLI, но DNS resolver Asterisk 20.6.0 сохраняет список
доступных типов транспорта со старта. Получался немедленный 503, cause=34;
служебный OPTIONS давал PJLIB_UTIL_EDNSNOANSWERREC. В исходниках это
res/res_pjsip/pjsip_resolver.c: sip_available_transports, sip_replace_resolver;
ast_sip_initialize_resolver вызывается при начальной загрузке res_pjsip.
Выполнен core restart gracefully при 0 активных каналах. Через 2 секунды
служба работала, home-iphone Connected=Yes/Free, оба доработанных модуля загружены.
Стационарный повторно зарегистрировался. Служебный OPTIONS через TLS получил 200 OK.
Временный endpoint проверки удалён. Сам сервер и соседние службы не перезапускались.

Применение после обновления/восстановления
Сначала сравнить актуальные настройки и сохранить их копии. Перенести раздел
transport-tls-linphone и параметры SRTP/TLS endpoint из указанного файла.
Существующий защищённый pjsip_linphone_push_auth.conf оставить без изменений.
Восстановить маршрут 612 выше, сохранив остальные маршруты. Выполнить
dialplan reload и module reload res_pjsip.so. Если TLS появился впервые,
нужен core restart gracefully при отсутствии разговоров. Затем проверить
подключение обоих телефонов и реальный вызов на 612, включая звук в обе стороны.
Проверку сертификата не отключать. Пароли T780P не менять.

Откат изменения SRTP/TLS
Вернуть только pjsip_linphone_push.conf из своей свежей резервной копии и
выполнить module reload res_pjsip.so. Если требуется полностью удалить новый
транспорт из памяти, завершить откат штатным перезапуском Asterisk при 0 звонков.
Старый вариант без SRTP несовместим с обязательным SRTP в Linphone и снова
получит 488; это откат конфигурации, а не рабочее решение исходной проблемы.
